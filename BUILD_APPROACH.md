# DriveScore — Build Approach & Considerations

*The 1–2 page write-up deliverable. Pre-filled from the design; `[fill after building]` marks slots that need real build results.*

## How I approached it — and what I prioritized / scoped out
I started from the judging rubric, not the feature list. The single highest-leverage thing is the **"it's real" proof**: a judge changing an input and seeing the output recompute live, with an AI explanation that's correct because it's reading the engine's actual numbers. So I built that round trip first (slider → `/score`/`/price` → live recompute → streamed `/explain`) and treated everything else as support for it.

I scoped the product down to **one story told through three views** — Driver Dashboard (Sarah, the safe driver overcharged ~S$420/yr), Live Rating Engine (the proof), Underwriter Console (the business case). Each view earns its place against a specific scored criterion; nothing is there "to look complete."

**Deliberately scoped out** (anti-criteria): auth, multi-user, persistence of edits, settings/account screens, tests, CI/CD, monitoring, and comprehensive error handling off the demo path. The data is synthetic and in-memory. The optional scikit-learn model is explicitly a "if there's time" item behind the rules engine, never on the critical path — so it can be cut without touching the demo.

## Technologies + reasoning
- **React + TypeScript + Vite, Tailwind, Recharts** — fast to build, polished by default, and Recharts covers the gauge, factor bars, and the quadrant scatter that carries the business view. Touchscreen-aware sizing because the Hub uses large touchscreens and the first 10 seconds set the impression.
- **Python on AWS Lambda** — the whole backend is a deterministic scoring/pricing function plus an LLM call; serverless keeps it ~$0 idle and makes one-command deploy trivial.
- **Live language model for the explanation** — the natural-language coach is generated by an actual LLM *at request time*, grounded in the engine's per-factor contributions (so it names the number it was handed). Two providers sit behind one interface: **Amazon Bedrock — Claude Sonnet 4.6** (`anthropic.claude-sonnet-4-6`, streamed via `converse_stream`) when AWS creds are present; otherwise a **keyless public LLM endpoint** so the AI runs live with *zero* credentials. Responses are cached by prompt (instant, reproducible) and degrade to a grounded template only if the model is unreachable — so removing the AI call visibly changes the output, but the demo never stalls.
- **Weighted-rules risk engine** (optionally backed by scikit-learn) — explainability is the feature; a transparent weighted formula lets every number be defended on camera and keeps the AI explanation faithful to the score.
- **AWS CDK** — one command stands up Lambda + Function URL + IAM + the S3 static site; reproducible clone-to-run.

## Tradeoffs given 5 days
- **Rules engine over a trained model as the source of truth.** A model might be marginally more "accurate," but on a synthetic dataset that's meaningless, and it would cost explainability and defensibility. The rules engine wins on every axis that's actually scored.
- **Sonnet over Opus.** Traded a little raw reasoning headroom for streaming latency — the right call when the AI output is a 2–3 sentence grounded summary and the demo is live.
- **In-memory synthetic data over a real datastore.** No DynamoDB/S3-data-lake plumbing; `drivers.json` is bundled. Costs nothing on the demo path and saves a day.
- **Cached AI fallback over robust retry logic.** Rather than harden the Bedrock call against every failure mode, a pre-baked explanation streams if the live call is slow or errors. Cheaper to build and it guarantees the demo never stalls — which matters more than handling a failure that won't happen on camera.
- **`/explain` on slider *release* only, not on every tick.** Keeps the score/price feedback instant while avoiding hammering Bedrock; a small UX call that protects latency and cost.

## What I'd do differently with more time
- Train and surface the optional **scikit-learn model** alongside the rules engine, showing the rules as a faithful explanation layer over it.
- Add a real **telematics ingestion path** (S3 data lake → batch scoring) instead of bundled JSON, to mirror the insurer's actual architecture.
- Per-driver **trend over time** (DriveScore improving as habits change) and a coaching nudge history.
- Underwriter **what-if controls** (move the base rate / multiplier slope and watch portfolio retention vs. loss trade off live).

## Making it production-realistic (post-MVP iteration)
Once the "it's real" core was solid, the biggest gap was that it *looked* like a metrics
prototype, not an insurance product. I added a **frontend presentation layer** over the
(untouched) engine so the demo reads like a real **Singapore motor product** — without faking
any number:
- **`domain.ts`** — SG policy chrome: policy number, comprehensive cover, **No-Claims Discount
  (0–50% SG scale)**, excess, cover dates, vehicle/plate, program tiers, and an **annualised
  SGD premium build-up** (base ± DriveScore behaviour adjustment − NCD = payable) shown against
  the standard rate-table.
- **`trips.ts`** — a deterministic recent-trips feed whose event density tracks the driver's own
  telematics (so it's consistent with the headline score).
- **`claims.ts` + `ClaimsHistory`** — a claims system-of-record that **validates the DriveScore**:
  Marcus's two at-fault claims link to the exact factors the model flagged (proving the static
  table underpriced a real loss-maker); Sarah's clean record proves she's overcharged. This turns
  "trust the model" into "your own claims confirm the model."
- **Persona switcher + light/dark theme** for the walkthrough (default light for a clean exec look).

## Making the business numbers defensible
The first cut hardcoded a loss-ratio improvement (84%→71%, a 13pp swing) — implausible to any
actuary. I replaced it with a **computed model** in `engine.py`: expected losses are anchored so
the static book sits on its filed target loss ratio (72%), then **adverse selection** (the
overcharged-safe drivers lapsing, `CHURN=0.30`) lifts the *before* ratio. Result: **75.8% → 72.0%
(−3.8pp)** — realistic for motor and derived live, so it survives scrutiny.

## Interesting challenges
- **Making the AI explanation provably correct, not plausible.** The win was grounding the prompt in the engine's per-factor contributions so the model *names the number it was handed* — when night-driving dominates, it says night-driving, every time. That's what makes the hero moment survive a skeptic.
- **Designing the static-vs-dynamic delta so the two failure modes fall out naturally.** The static table had to over-price the safe cohort and under-price the risky cohort by construction, so the Underwriter Console's two quadrants are populated and the repricing story is real, not asserted.
- **Keeping the live recompute genuinely live under extreme inputs.** Clamping `norm()` and the multiplier means a judge dragging a slider to the rail gets a saturated-but-coherent result, never a NaN or an absurd premium — the demo stays unbreakable on the path that's on camera.
- **One palette, two styling paths.** The app colours come from both Tailwind utilities and inline styles; to make a single theme toggle repaint everything, `theme.ts` writes the palette as CSS variables (hex + `-rgb` channels for Tailwind's `<alpha-value>`) *and* exposes a live Proxy token object that inline styles read on the next render.
- **Loss ratio that points the right way.** First attempt anchored expected losses to the dynamic book, which made static pricing look *better* — backwards. Re-anchoring to the static book's filed target, with adverse selection as the only mover, produced the correct, modest, defensible direction.

## Build results (verified)
- **Frontend build** passes (`tsc --noEmit` + Vite, ~590 kB JS); both servers run via `./scripts/dev.sh` and the `/api` proxy reaches the backend.
- **Live recompute confirmed** end-to-end: Sarah (D0001) score 91, S$68/mo dynamic vs S$103 static; pushing night-driving 35%→60% drops the risky applicant 30→22 and re-rates the premium up, with `/explain` streaming and naming night-driving.
- **Loss-ratio model:** 75.8% → 72.0% (−3.8pp); retention +6.2pp; ~S$3.5M/yr loss leakage recovered (50k-policy modelled book).
- **Live AI verified:** the `/explain` coach is genuinely **model-generated** — verified end-to-end, it names the dominant factor correctly (e.g. night-driving) and the prose changes with the inputs. Default path is a **keyless LLM (no AWS creds)**; `USE_BEDROCK=1` switches to Bedrock/Claude. `/health` reports `explain_source:"llm"`. The free endpoint rate-limits bursts, so demo scenarios are pre-warmed into an on-disk cache (instant, reproducible) and any unreachable call degrades to the grounded, engine-faithful template — the guaranteed-never-stall safety net.
- **Cloud deploy** remains deferred per the brief (CDK stub); local run is the supported path.
